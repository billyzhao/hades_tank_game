# 《废土中继》多智能体协同与项目治理设计

## 0. 2026-07-18 执行模式修订（优先于本文旧角色流程）

用户确认项目改用单主智能体开发模式，并提供《任务分级规则》《智能体规则》。自本修订起：

- 主智能体统一承担制作人、策划、架构、开发、测试和最终验收。
- 默认禁止子智能体；只有重大任务存在两个以上完全独立、真正可并行且不修改同一文件组的工作时，最多临时启动两个。
- 快速任务采用“直接修改→最小测试→完成”；标准任务采用“验收标准→方案→实现→相关测试→自检”；重大任务由主智能体先确定完整架构和接口。
- 本文中要求“每迭代创建角色智能体”“双门禁由多个角色依次执行”的历史规则，改为主智能体的单人前置检查、实现、自检和后置验证，不再强制委派。
- 方案偏离确认、用户验收前禁止提交/推送、Godot 可见验证不可被自动化替代等约束继续有效。

### 0.1 2026-07-18 执行节奏修订（优先于历史的逐子任务门禁表述）

07B 执行复盘确认：当前项目未启动子智能体；进度变慢的直接原因不是多智能体协同，而是主智能体将测试先行和计划拆分机械化为“每个私有接口都单独红绿，再执行全量构建并汇报”。该做法与单主智能体规则中的“最小充分测试”冲突。

- 以玩家可见的最小玩法闭环作为迭代内的首个交付目标；内部基础设施不得抢占核心可玩路径。
- 以功能块而非私有接口作为验证边界；默认连续完成迭代内的开发内容，不能因为单个方法或私有接口变动就中断为验证门禁。
- **完整构建、全部 headless 套件、Godot 启动、策划可见验收和回归检查统一在迭代开发完成后执行。**
- 开发中仅为无法继续的编译诊断、明确失败修复，或伤害/状态机/资源写入等高风险规则保留单个定向检查；定向检查不得升级为全量验证。
- 该修订不削弱 TDD：关键玩法规则仍须先有能失败的测试；仅取消对同一功能块内每个微小接口的重复全量流程。

## 1. 目的

本设计规定《废土中继》后续迭代如何使用策划、测试、开发和架构审查智能体协作，同时保证所有实现严格服从已确认的策划方案、技术架构、开发计划、素材授权和策划验收标准。

本设计不改变游戏玩法或当前技术架构。它只建立项目治理、任务交接、架构约束、测试门禁、偏离处理和仓库操作规则。

## 2. 核心原则

1. 主智能体是项目的总制作人，同时承担主策、主美把关和主程序/架构负责人的最终责任。
2. 子智能体负责专业执行，但没有改变项目方向、技术架构或验收标准的权力。
3. 每个迭代重新创建一组角色智能体；所有角色必须从最新已确认文档重新建立上下文。
4. 开发采用双门禁：开发前由策划和测试锁定需求与验证方式，开发后由架构、测试和策划依次复验。
5. 任何实质偏离都必须暂停受影响任务，向用户说明并获得确认；确认后先更新相关文档，再继续开发。
6. 开发智能体的自我声明不构成完成证据。完成必须由代码差异、自动化测试、运行时验证、架构合规矩阵和策划验收共同证明。
7. 用户完成验收前，不提交、不推送仓库；只有主智能体可以执行最终提交和推送。

## 3. 权威来源与优先级

发生冲突时，按以下顺序裁决：

1. 用户最新明确确认的决定；
2. 已确认的游戏策划文档；
3. 已确认的技术设计文档；
4. 已确认的开发计划；
5. 素材流程、授权登记和验收文档；
6. 当前迭代执行记录；
7. 智能体任务说明和临时报告。

若两个上层文档互相冲突，任何智能体都不得自行选择。主智能体必须暂停受影响任务、说明冲突及影响，并请求用户确认。确认后先修订权威文档。

## 4. 角色与权限

### 4.1 主智能体

主智能体是唯一面向用户的项目总控，职责包括：

- 维护策划、技术、美术、开发计划和验收标准的一致性；
- 根据最新文档划定迭代目标、范围和文件边界；
- 创建、调度和回收本迭代角色智能体；
- 审核策划方案、测试矩阵、开发理解回执和代码差异；
- 裁决普通实现问题，识别并上报实质偏离；
- 以主程序身份执行架构合规检查；
- 以总制作人身份汇总策划、测试、美术表现和技术结果；
- 持续向用户汇报进度；
- 完成独立自检并准备用户验收包；
- 仅在用户明确验收通过后执行提交和推送。

主智能体不能因为任务已经委派，就用子智能体的报告替代自己的验证。

### 4.2 策划智能体

策划智能体负责：

- 阅读当前策划、技术、计划和已有实现；
- 把迭代目标拆为玩法规则、边界条件、表现要求和成功标准；
- 发现需求歧义、规则冲突和范围偏离；
- 编写或修订策划内容与“操作 → 预期画面/数值/状态变化”验收脚本；
- 开发完成后，从玩法、可读性、节奏和用户体验角度复验。

策划智能体不得修改生产代码，不得改变已确认技术架构，也不得代替用户进行最终验收。

### 4.3 测试智能体

测试智能体负责：

- 在开发前根据需求和架构制定测试矩阵；
- 为适合自动化的要求先建立能够失败的测试；
- 编写单元测试、场景/集成测试、架构合规检查和策划可见测试脚本；
- 开发后执行回归、边界、异常、运行时和游戏体验测试；
- 提供可复现的失败步骤、期望结果、实际结果和证据。

测试智能体只修改获准的测试文件和测试报告。它不得修改生产代码，不得删除或弱化测试来迁就实现。

### 4.4 开发智能体

开发智能体负责：

- 按开发任务合同实现生产代码；
- 在编码前提交需求—文件—接口—测试映射；
- 使用测试驱动方式分小步实现；
- 每个子任务结束后报告完成条款、修改文件、测试结果和风险；
- 发现文档冲突、架构不可行或需要简化时立即暂停并上报。

开发智能体没有设计权。它不得擅自改变玩法、架构、依赖、场景结构、数据流、输入、素材授权或验收标准，也不能用硬编码或临时替代方案绕开已确认设计。

### 4.5 架构审查智能体

状态系统、数据驱动内容、导航、存档、场景生命周期、跨模块重构等高风险任务，增加一个独立、只读的架构审查智能体。它负责：

- 对照技术设计和开发任务合同检查代码差异；
- 查找硬编码、职责越界、错误依赖方向、共享资源运行时修改和未批准的替代实现；
- 输出不修改代码的合规报告。

架构审查智能体不能替代主智能体的最终架构裁决。

## 5. 智能体生命周期与写入隔离

- 每个迭代重新创建角色智能体，迭代结束后回收；
- 新智能体不继承旧智能体的口头结论，只读取最新已确认文档和当前代码；
- 同一时间不允许两个智能体修改同一组文件；
- 策划、测试、开发任务按阶段交接；可并行的只读调查可以并行；
- 每个写入任务都必须列出允许修改和禁止修改的文件；
- 主智能体通过任务前后的 Git 状态与完整差异审计写入范围。

协作环境不能提供真正的操作系统级文件权限隔离，因此文件边界由任务合同、顺序执行和 Git 差异审计共同约束。越界修改视为任务失败，不能进入下一门禁。

## 6. 开发任务合同

开发前，主智能体必须从权威文档生成开发任务合同。合同至少包含：

- 迭代目标与非目标；
- 权威文档路径和当前版本；
- 必须实现的规则、接口、节点结构、状态机和数据流；
- 必须保持不变的架构约束；
- 明确禁止的实现方式；
- 允许新增、修改和禁止修改的文件；
- 必须先建立的测试；
- 构建、自动化、Godot 运行和策划验收命令；
- 需要暂停并申请偏离确认的条件。

开发智能体收到合同后，必须先提交实现理解回执，包括：

- 每条需求计划在哪个文件实现；
- 对应哪条技术架构约束；
- 将新增或保持哪些公开接口；
- 将先建立哪些失败测试；
- 已发现的冲突、风险或缺失信息。

主智能体批准理解回执前，开发智能体不得开始写代码。

## 7. 双门禁迭代流程

### 7.1 迭代启动

主智能体读取最新文档、代码、测试和 Git 状态，确定迭代目标、非目标、权威文档版本和角色任务。

### 7.2 策划前置门禁

策划智能体提交玩法规则、边界条件、表现要求和策划可见验收脚本。主智能体审核其与现有方案的一致性。若需要改变方案，进入偏离流程。

### 7.3 测试前置门禁

测试智能体建立测试矩阵。适合自动化的要求先写失败测试并证明测试能够捕捉缺失功能。测试范围至少覆盖本迭代新增功能、相关回归和已知边界。

### 7.4 开发理解门禁

主智能体发布开发任务合同，开发智能体提交理解回执。回执审核通过后才开始开发。

### 7.5 开发执行

开发智能体按小任务实现并持续报告。每个小任务都必须形成“方案条款 → 实现位置 → 测试证据”的对应关系。

### 7.6 架构合规门禁

主智能体检查完整代码差异和文件边界，建立架构合规矩阵。高风险任务再由只读架构审查智能体独立复核。不合规的实现退回开发，不能进入功能测试。

### 7.7 测试后置门禁

测试智能体执行完整测试矩阵。失败项返回开发智能体修复；修复后必须重新经过受影响的架构检查和测试，不能带已知失败进入策划验收。

### 7.8 策划复验

策划智能体按策划验收脚本验证玩法是否符合设计、画面和 HUD 是否可理解、关键状态是否可见、操作路径是否真实可执行。只存在于代码中但玩家无法观察的功能，视为验收失败。

### 7.9 主智能体最终自检

主智能体独立执行构建、测试、Godot 烟测和必要的人工玩法验证，并核对文档、素材登记、工作区状态和架构合规矩阵。

### 7.10 用户验收与仓库操作

全部内部门禁通过后，主智能体交付策划式验收包。只有用户明确验收通过后，主智能体才可提交并推送 `main`。

## 8. 架构合规矩阵

每个迭代至少记录：

| 架构条款 | 实现文件/接口 | 自动化或运行证据 | 状态 |
|---|---|---|---|
| 技术文档规定的约束 | 精确实现位置 | 测试、构建或场景验证 | 符合、偏离或不适用 |

任何“偏离”项都必须附用户确认记录和已更新文档链接；没有确认记录的偏离不能交付。

## 9. 实质偏离门禁

以下情况属于实质偏离，必须暂停并请求用户确认：

- 玩法规则、数值逻辑、玩家操作或表现语义变化；
- 策划范围、迭代顺序、验收标准或成功定义变化；
- 技术架构、引擎版本、关键依赖、数据结构或模块边界变化；
- 取消、简化、替换文档规定的功能或实现方式；
- 新素材来源、授权条件或购买费用变化；
- 用户临时想法与现有权威文档不一致。

以下属于正常实现细节，不需要单独确认：

- 私有变量、私有方法和局部命名；
- 不改变外部行为和架构边界的内部整理；
- 恢复文档规定行为的缺陷修复；
- 注释、日志和测试代码的常规调整；
- 文档明确允许范围内的实现细节。

偏离处理固定为：

```text
发现偏离 → 暂停受影响任务 → 说明原方案、原因、影响和选项
→ 用户确认 → 先更新策划/技术/计划/验收/素材文档 → 恢复开发
```

## 10. 迭代执行记录

每个迭代建立一份统一记录，建议路径为：

```text
docs/iterations/iteration-NN-<topic>.md
```

记录包含：

- 目标、非目标和权威文档版本；
- 策划验收标准；
- 开发任务合同和文件边界；
- 测试矩阵；
- 架构合规矩阵；
- 门禁与实际进度；
- 偏离申请和用户结论；
- 最终测试、策划验收、用户验收、提交和推送状态。

该记录是执行台账，不替代策划、技术或开发计划。发生方案变化时必须同步修改真正的权威文档，不能只写进迭代记录。

## 11. 异常处理

- 开发与测试理解不一致：以权威文档和已确认验收标准为准；若文档不明确则暂停确认；
- 代码能运行但违反架构：判定开发失败并退回；
- 测试通过但策划不可见：判定策划验收失败，补充 UI、反馈或验收入口；
- 智能体卡住或持续给出无效结果：主智能体停止该智能体，审计已有改动，再创建新的本迭代角色智能体接管；
- 智能体误改同一文件：立即停止写入，由主智能体审计和裁决，不允许智能体自行合并；
- 文档没有覆盖关键选择：判定为方案缺口，开发智能体不能自由发挥；
- 测试环境问题：先区分环境故障与产品故障；没有证据前不能把失败标记为通过。

## 12. 进度沟通

- 主智能体在迭代启动、门禁完成、发现问题、发生偏离、验证完成时主动汇报；
- 长时间构建、测试、生图或运行期间，原则上不超过约 60 秒没有进度更新；
- 子智能体只向主智能体汇报，由主智能体整理后面向用户输出；
- 普通技术问题由主智能体持续推进；只有需要改变方案、扩大权限或用户作出实质选择时才暂停等待；
- 进度更新必须说明当前阶段、已完成内容、正在执行内容和是否需要用户操作。

## 13. 每次交付的必要证据

用户验收包至少包含：

- 本迭代依据的权威文档版本；
- 实际修改文件和功能摘要；
- 架构合规矩阵；
- 自动化测试、Debug/Release 构建和 Godot 运行结果；
- 策划验收脚本，格式为“操作 → 预期画面/数值/状态变化”；
- 已知风险和未完成项；
- 偏离情况；若无实质偏离，明确写明“未发现实质偏离”；
- 是否满足提交、推送条件。

## 14. 落地范围

本协同治理方案从下一次正式开发迭代起执行。落地前先完成当前文档基线整理：回填既有迭代状态、记录已确认的原型期架构简化、更新素材与 README 状态，并建立项目级智能体指令入口。具体文件修改和验证步骤由后续实施计划定义。
