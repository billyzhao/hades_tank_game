# 迭代 06：协议构筑与双战斗循环设计

## 1. 目的与依据

本设计将 MVP Task 6 拆为两个可独立验收的开发迭代，保持既有玩法方向不变：第一场守点战结束后出现军械协议三选一，所选构筑持续影响后续战斗；随后再引入第二个不同布局的战斗房间。

本设计以以下已确认文档为准：

- [游戏策划](./2026-07-15-roguelite-tank-design.md)；
- [技术设计](./2026-07-15-roguelite-tank-technical-design.md)；
- [MVP 开发计划 Task 6](../plans/2026-07-15-roguelite-tank-mvp.md#task-6协议构筑三选一与第二场战斗)；
- [原型架构暂缓决策 0001](../../decisions/0001-prototype-architecture-deferrals.md)；
- [项目协同治理设计](./2026-07-17-agent-collaboration-governance-design.md)。

本文件是对 Task 6 的执行拆分，不改变其玩法目标、技术架构或内容边界。后续实现前仍需经过测试前置、架构审查与用户对实施计划的确认。

## 2. 拆分决定

| 迭代 | 可玩成果 | 偿还/保持的架构边界 |
|---|---|---|
| 06A：协议与奖励循环 | 第一场战斗结束后进入三选一；选择永久写入本局构筑；以派生种子重新进入现有战斗房，验证构筑在第二场同布局战斗中生效。 | 偿还 `ProtocolDefinition`、运行时构筑作用域、确定性奖励和完整房间生命周期。暂不新增不同布局，因此不触发 TileMap/A* 门槛。 |
| 06B：第二房间与导航偿还 | 在保留构筑的前提下，进入第二个不同布局的战斗房；砖墙/钢墙由 TileMapLayer 表达；敌军可在地形变化后使用可更新的 A* 导航。 | 偿还 `RoomDefinition`、TileMap 地形与可更新导航门槛。保持普通敌人池不扩充，因此不提前触发 `EnemyDefinition`/策略迁移门槛。 |

“第二场战斗”在 06A 中指对现有房间以派生种子重新开战，用于验证跨房间 RunState、协议和奖励闭环；“第二个不同布局房间”只在 06B 引入。两者必须明确区分，不能把同一房间的重开描述为新增房间内容。

## 3. 06A 玩法与用户体验

### 3.1 房间流程

房间状态固定为：

```text
Loading → Intro → Combat → Cleared → Reward → Exiting
                    └──────────────→ Failed
```

- `Intro`：显示 0.6 秒部署提示；敌军生成预警可见，但尚未造成伤害。
- `Combat`：延续当前三波守点规则。
- `Cleared`：冻结生成、清理危险炮弹并显示“战场清理完成”。
- `Reward`：战斗逻辑暂停，奖励面板显示三个协议卡；玩家只能选择其中一个。
- `Exiting`：记录选择、释放旧房间、保留 `RunState`，然后重新实例化现有战斗房并使用派生种子开始下一战。
- `Failed`：仅能从 `Combat` 进入，沿用中继站归零或重启耗尽失败规则；失败时不能出现奖励面板。

### 3.2 协议内容与构筑规则

首批协议保持 MVP Task 6 已确认的十项内容，不在 06A 擅自扩池：

| 类别 | 协议 | 可见效果 |
|---|---|---|
| 前线兵工局 | 额外反弹、反弹伤害 +30%、首次命中后分裂、射速提升但伤害降低、重炮弹但射速降低 | 改变炮弹轨迹、命中或射击节奏。 |
| 侦察电子组 | 电能冲刺履带、冲刺冷却 -20% | 改变冲刺后的区域控制与机动频率。 |
| 后勤维修署 | 房间清场修复装甲、房间清场修复中继站 | 清场进入奖励前可见地恢复双生命线。 |
| 工程兵团 | 中继站拦截护盾 | 对中继站受击产生可读的拦截反馈。 |

至少两组联动必须可被验收：

- 反弹数量 + 反弹伤害：窄巷钢墙反弹路线造成明显更高伤害；
- 电能冲刺履带 + 冲刺冷却：更频繁冲刺留下持续伤害/控制区域。

协议定义是只读 `Resource`；每局选择记录在普通 C# `RunState` 的构筑状态中。效果只能通过受控事件钩子作用于本局快照或战斗事实，不能修改 `.tres` 定义、静态基础数值或下一局状态。

### 3.3 确定性奖励

相同的局种子、房间索引、已选协议集合与内容目录版本必须生成相同的三项候选，候选必须：

- 恰好三项、ID 唯一；
- 排除冲突协议和已达叠加上限协议；
- 至少保留一个通用候选，避免协同权重替玩家完成决策；
- 在候选生成前固定排序内容 ID，禁止依赖资源加载或字典枚举顺序。

## 4. 06A 技术边界

### 4.1 数据与运行时边界

- `ProtocolDefinition` 和 `ProtocolEffectDefinition` 保存 ID、部门、稀有度、标签、数值参数、冲突/前置条件与叠加上限；
- `ContentCatalog` 在进入战斗前验证唯一 ID、空引用、数值范围和前置条件；调试构建报告明确错误，发布构建返回应用壳而非带坏数据进入战斗；
- `BuildController` 只拥有当前 Run 的已选协议和订阅；Run 结束或切回应用壳时必须解除订阅；
- `StatPipeline` 以“基础值 → 固定值 → 加法百分比 → 乘法百分比 → 最终钳制”的顺序计算，不把协议数值硬编码到玩家、武器或 HUD；
- `RewardGenerator` 只生成候选，不直接修改构筑；`RewardScreen` 只报告选择；`RunController` 才写入 RunState 并负责房间切换。

### 4.2 明确不做

- 不新增第二个不同布局房间；
- 不替换当前砖墙为 TileMapLayer，也不提前实现 A* 导航；
- 不扩充普通敌人池、不迁移 EnemyDefinition/独立行为策略；
- 不加入商店、维修房、路线选择、局外解锁、Boss 或存档；
- 不为协议新增一套未确认的视觉/音频资源体系。

## 5. 06A 测试与策划验收

### 5.1 自动化测试门槛

- 统计管线：基础 10、固定 +2、加法 +50%、乘法 ×2，结果必须为 36；
- 确定性：相同输入生成相同有序候选；不同派生房间种子可改变候选；
- 候选约束：无重复、无冲突、无满层项，且存在通用候选；
- 本局作用域：协议加入后影响指定快照/事件，重开 Run 后不残留；
- 状态机：只能从 `Combat` 失败；清场后必须经过 `Reward` 与 `Exiting`；选择后只开始一次下一战；
- 内容校验：重复 ID、非法范围、缺失引用和无满足前置条件的内容均被拒绝。

### 5.2 可见验收脚本

| 操作 | 预期画面/状态 |
|---|---|
| 完成现有三波战斗 | HUD 显示 Cleared，危险炮弹清理，随后进入 Reward 而不是直接重开。 |
| 观察奖励面板 | 居中显示三张可读协议卡，包含部门色、名称、效果说明和已选构筑摘要；战场输入冻结。 |
| 选择反弹类协议 | 面板关闭，事件栏记录协议 ID，进入 Exiting 后重新开始同布局下一战；HUD 构筑栏保留该图标。 |
| 在下一战向钢墙开火 | 额外反弹或反弹伤害的效果可见，且与未选择时不同。 |
| 选择冲刺联动的两项协议后进入下一战 | 冲刺冷却缩短，履带电场可见并能作用于敌人。 |
| 令中继站或重启耗尽失败 | 直接进入失败流程，不出现 Reward 面板。 |

## 6. 06B 玩法与技术边界

### 6.1 第二个不同布局房间

06B 新增一张同属黄沙废土工业区、但与现有房间路线/掩体不同的战斗房。它复用已确认的三类敌人与守点目标，不新增敌人类别或 Boss。房间差异必须让玩家能感受到协议在不同掩体与路线条件下的价值，而不是只镜像翻转现有地图。

房间数据由 `RoomDefinition` 驱动，至少包含房间场景、出生点/波次、玩家与中继站位置、奖励类别和派生种子规则。`RunController` 根据房间索引选择定义并实例化，而不是以场景路径或波次预算硬编码切换。

### 6.2 TileMap 与导航

- 地面、砖墙、钢墙使用 Godot 4.7 `TileMapLayer` 分层；TileSet 自定义数据提供地形种类、耐久、反弹与阻塞导航信息；
- 砖墙的运行时耐久由 `DestructibleTerrain` 保存，击破只擦除对应格子，不修改 TileSet 静态资源；
- `NavigationGrid` 从阻塞格构建 `AStarGrid2D`，砖墙消失或动态阻挡变化时只更新受影响格；
- 敌军重算最多每秒四次并错峰；没有路径时使用安全的直接操控回退，不得卡死；
- 06B 不新增实体敌方炮弹，因此不触发重启清弹/短暂无敌的另一项偿还门槛。

### 6.3 06B 验收

| 操作 | 预期画面/状态 |
|---|---|
| 完成 06A 的第一场并选择协议 | 下一战进入明显不同的第二房间，HUD 构筑与双生命线持续保留。 |
| 破坏挡路砖墙 | 砖格消失；敌军在有限时间内重算路线并继续向目标推进。 |
| 观察钢墙与反弹协议 | 钢墙仍不可破坏并保持反弹；反弹构筑在第二房间的窄巷可读。 |
| 让敌军找不到完整路径 | 敌军采用安全直接操控回退，不冻结、不穿过阻塞墙。 |
| 重开相同种子短局 | 两张房的顺序、波次、奖励候选保持确定性。 |

## 7. 协同与门禁

每个子迭代都使用新的策划、测试、开发与只读架构审查智能体：

1. 主智能体先确认本设计、测试矩阵与迭代合同；
2. 测试智能体先写可失败的测试与可见验收脚本；
3. 开发智能体只能按批准的文件边界和接口实现；
4. 架构审查智能体检查 Resource 只读、RunState 作用域、房间生命周期、TileMap/A* 门槛与信号释放；
5. 测试与策划复验通过后交用户验收；
6. 用户明确验收通过前，不提交或推送。

任何将 06A 直接扩展为第二个不同布局房间、绕过 TileMap/A*、用硬编码奖励替代资源数据、或在未确认条件下改变协议池的做法，都是实质偏离，必须暂停并先更新本设计与相关权威文档。
